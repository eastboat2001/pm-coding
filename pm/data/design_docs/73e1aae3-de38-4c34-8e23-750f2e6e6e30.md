# System Design Document

> **Project:** D.CHQ.QDM Finished Lot Yield Dashboard  
> **Status:** Draft / Implementation-Ready  
> **Version:** 1.0  
> **Tech Stack:** C# (Backend), SQLite (Database), Vanilla JS/HTML/CSS (Frontend)

---

## 1. Scope and Objectives

### 1.1 Background
The dashboard provides high-level views of current key yield metrics for different products in the factory. It is updated by an automated scheduled script every day so QDM and yield teams can review current finished-lot performance without manual report preparation.

### 1.2 Objectives
- Visualize yield improvement curves to drive production cost reduction.
- Expose overall yield trends, drill-down segments, and product views.
- Identify root causes via loss-code Pareto and loss-operation attribution.
- Recover investment costs sooner by optimizing production output visibility.

### 1.3 In Scope
- **Finished Lot Performance Overview Trend:** Weekly yield, Output, and NSQM Loss.
- **Loss Ratio By Defect Code:** Top 10-20 defect Pareto, trends, and department distribution.
- **Unified Filters:** Customer, Plant, Date Type, Lot Type, Unit Type, and Project Type.
- **Calculation Engine:** Lot-level and weekly aggregated product yield logic.

### 1.4 Out of Scope
- Automated process-parameter optimization.
- Formal QMS defect disposition workflow replacement.
- Supplier or customer complaint management.

## 3. System Use Cases

### 3.1 UC-01: Review Weekly Performance
- **Actor:** Yield Team / Manager
- **Trigger:** User navigates to the Overview page.
- **Preconditions:** Data sync from DS-01 is complete.
- **Main Flow:**
    1. System loads default filters (Weekly, HVM, NSQM, Overall).
    2. System renders the "Weekly Finished Lot Performance Overview Trend" line chart.
    3. System displays summary cards for latest-week Output, Yield, and NSQM Loss.
- **Postconditions:** User sees the current state of production yield.
- **Acceptance Checks:** Values match DS-01 source for the current week.

### 3.2 UC-02: Interactive Drill-Down
- **Actor:** Engineer
- **Trigger:** User clicks a specific week/segment on the trend chart.
- **Preconditions:** Trend chart is populated.
- **Main Flow:**
    1. User clicks a data point on the left-side trend chart.
    2. System captures the selected time range/segment.
    3. System refreshes the right-side detail panel to show specific lot/product data for that selection.
- **Postconditions:** Detail panel reflects the selected context.
- **Acceptance Checks:** Visual indicator shows which segment is active.

### 3.3 UC-03: Defect Pareto Analysis
- **Actor:** Manager / Yield Team
- **Trigger:** User switches to the "Loss Ratio By Defect Code" page.
- **Main Flow:**
    1. System fetches top 20 defect codes from DS-02.
    2. System renders a Pareto/Stacked Bar chart.
    3. User clicks a defect bar; the right-side trend and department pie chart update.
- **Postconditions:** User identifies the primary driver of yield loss.

## 4. Functional Requirements

- **FR-01: Unified Filter Bar:** Must support multi-select for Customer/Plant and single-select for Date Type/Lot Type.
- **FR-02: Yield Calculation:** Must implement `GTY = Product(Process_Yield_n)` where `Process_Yield = Output / Input`.
- **FR-03: Data Export:** Users with permission can export the current view's underlying data to CSV/Excel.
- **FR-04: Responsive UI:** Charts must resize dynamically for desktop and tablet resolutions.

---

## 5. Non-Functional Requirements

- **Performance:** Chart refresh should complete within < 3 seconds for standard queries.
- **Availability:** Dashboard available 24/7; data refresh occurs daily via scheduled script.
- **Usability:** Follows AITC color system; tooltips must be touch-friendly.
- **Browser Support:** Optimized for latest Chrome and Edge.

---

## 6. High-Level Architecture

The system follows a lightweight 3-tier architecture:
1.  **Frontend:** Static HTML/CSS/Vanilla JS using Bootstrap for layout and a charting library (e.g., Chart.js or D3.js).
2.  **Backend:** C# (ASP.NET Core Minimal API) providing RESTful endpoints.
3.  **Database:** SQLite for local storage of aggregated summary data (DS-01, DS-02).

---

## 7. Module Responsibilities

- **Data Ingestion Service (C#):** Scheduled task to pull data from QDMProductionDB into the local SQLite instance.
- **API Layer (C#):** Handles filter logic, data retrieval, and yield aggregation.
- **UI Controller (JS):** Manages state, filter synchronization, and chart rendering.
- **Export Engine:** Generates downloadable files based on the current filtered dataset.

## 9. Data Model and Database Design

### 9.1 Tables

#### Table: `FinishedLotSummary` (Ref: DS-01)
| Field | Type | Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `ID` | INTEGER | PK, AutoInc | Internal ID |
| `ATSDate` | DATETIME | Index | Date of record |
| `DateType` | TEXT | Index | Weekly, Monthly, Quarterly |
| `Customer` | TEXT | Index | Customer Name |
| `Plant` | TEXT | Index | Plant Location |
| `LotType` | TEXT | - | HVM, Prototype, etc. |
| `Yield` | REAL | - | Calculated Yield % |
| `Output_NSQM` | INTEGER | - | Output quantity |

#### Table: `DefectSummary` (Ref: DS-02)
| Field | Type | Constraints | Purpose |
| :--- | :--- | :--- | :--- |
| `ID` | INTEGER | PK, AutoInc | Internal ID |
| `ATSDate` | DATETIME | FK -> Summary | Date of record |
| `DefectCode` | TEXT | Index | Code identifier |
| `DefectQty` | INTEGER | - | Quantity lost |
| `Department` | TEXT | - | Responsible Dept |
| `LossRatio` | REAL | - | Calculated loss % |

### 9.2 Constraints & Retention
- **Consistency:** `ATSDate` and `DateType` must align across both tables for joins.
- **Retention:** Keep 24 months of historical data; older records archived annually.

## 10. Key Workflows / Sequence Narratives

1.  **Data Load:** The C# backend queries the SQLite DB for records matching the default filter set.
2.  **Aggregation:** If the user selects "Monthly," the backend aggregates weekly records into monthly buckets.
3.  **Visualization:** The JS frontend receives JSON, clears existing chart objects, and re-initializes them with new data.
4.  **Interaction:** Clicking a bar in the Pareto chart triggers a secondary API call to fetch the "Trend by Defect Code" for the right-side panel.

---

## 11. Security, Privacy, and Compliance

- **Authentication:** Integrated with Enterprise Single Sign-On (SSO).
- **Authorization:** Role-based access (Admin vs. Viewer). Export functionality restricted to "Yield Team" and "QDM" roles.
- **Data Privacy:** No PII (Personally Identifiable Information) stored; data is limited to manufacturing metrics.

---

## 12. Observability and Operations

- **Logging:** Backend logs API request duration and errors to a local file/Serilog.
- **Health Check:** `/api/health` endpoint to verify SQLite connectivity.
- **Data Freshness:** UI displays "Last Updated" timestamp based on the latest record in `FinishedLotSummary`.

## 13. Deployment and Environment Plan

- **Dev:** Local SQLite, C# Debug mode.
- **Test/QA:** Shared staging server with a copy of production data.
- **Prod:** IIS hosting the C# API and static frontend; SQLite file stored on a persistent volume.

---

## 14. Testing and Acceptance Plan

- **Data Validation:** Compare dashboard "Yield %" against manual Excel calculations for 5 random lots.
- **UI Validation:** Verify "No Data Found" state by filtering for a non-existent plant/date combo.
- **Performance:** Ensure page load < 3s with 10,000 records in SQLite.

---

## 15. Risks, Trade-offs, and Assumptions

- **Assumption:** The yield formula provided (multiplication of process yields) is the final approved version.
- **Risk:** SQLite performance may degrade if the dataset grows beyond 5 years of granular data.
- **Trade-off:** Using Vanilla JS instead of a framework (React/Vue) reduces build complexity but requires more manual DOM manipulation for chart updates.
