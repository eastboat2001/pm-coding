## 1. 范围与目标

- **项目名称**: D.CHQ.QDM Finished Lot 良率看板
- **需求名称**: Finished Lot 绩效趋势与缺陷损失占比看板
- **背景说明**: 该看板旨在为工厂提供不同产品良率指标的高层视图，通过自动化脚本每日更新，取代传统手工报表。
- **目标**: 
    - 展示整体良率趋势与下钻分析。
    - 通过 Pareto 图识别 Top 缺陷及损失工序。
    - 明确根因责任归属，加速良率改善曲线，降低生产成本。
- **本次范围**: 
    - 两个核心页面：Finished Lot Performance Overview Trend 和 Loss Ratio By Defect Code。
    - 统一筛选器契约与联动交互。
    - 批次级与周汇总良率计算逻辑实现。
- **非本次范围**: 自动优化工艺参数、替代正式 QMS 判定流程、供应商/客户投诉管理、自助 BI 建模。

## 2. 用户角色与参与方

- **Yield Team (业务/数据负责人)**: 负责指标定义、源数据提供、UI 评审及最终 QA 测试。
- **QDM Team (产品/研发负责人)**: 负责产品定义、前端开发（HTML/JS）及系统维护。
- **QA 团队**: 负责数据准确性验证及响应式 UI 验收。

## 3. 系统用例

### 用例 1：查看良率绩效趋势
- **参与者**: Yield Team 工程师/经理
- **触发条件**: 用户访问 Quality Operation Center 门户。
- **前置条件**: 用户已获得系统访问权限，DS-01 数据已同步。
- **主流程**:
    1. 系统加载默认筛选条件（Weekly, HVM, NSQM, Overall）。
    2. 系统从后端获取 Finished Yield 趋势数据。
    3. 页面渲染左侧折线图（CH-01）和右侧最新周明细卡片。
- **后置条件**: 用户看到当前业务状态的直观视图。
- **验收检查点**: 图表数值与 QDM 源表一致，Tooltip 显示正确。

### 用例 2：多维筛选联动分析
- **参与者**: QDM 用户 / 工程师
- **触发条件**: 用户修改筛选栏中的任一条件（如 Plant 或 Date Type）。
- **前置条件**: 页面已加载。
- **主流程**:
    1. 用户在筛选栏选择新的过滤值。
    2. 前端捕获变更事件，异步请求后端 API。
    3. 后端根据新参数重新计算/查询数据。
    4. 页面所有图表（趋势图、Pareto 图、明细表）在不刷新整页的情况下更新。
- **备选流程**: 若筛选条件下无数据，图表应显示“No Data Found”占位符。
- **验收检查点**: 筛选上下文在导出时被保留，交互无明显延迟。

### 用例 3：缺陷损失根因下钻
- **参与者**: 经理 / 质量工程师
- **触发条件**: 用户点击 Loss Ratio By Defect Code 页面中的特定缺陷分段。
- **主流程**:
    1. 用户查看 Top 20 缺陷 Pareto 图。
    2. 点击某一高损失缺陷代码。
    3. 右侧“缺陷趋势”和“原因部门分布”图表立即切换为该特定缺陷的数据。
- **验收检查点**: 选中状态有视觉高亮，右侧图表标题同步更新。

## 4. 功能需求

### 4.1 功能明细表
| 功能模块 | 描述 | 关键逻辑 |
| :--- | :--- | :--- |
| **趋势看板** | 展示 Finished Yield 趋势 | 按 ATSDate 聚合，计算连续乘积良率。 |
| **缺陷分析** | Top 10-20 缺陷 Pareto | 按 DefectQty 降序排列，计算 Loss Ratio。 |
| **统一筛选** | 跨页面共享筛选上下文 | 支持 Customer, Plant, Date Type 等 6 个维度。 |
| **数据导出** | 导出图表及底层数据 | 需包含当前筛选条件，遵循权限控制。 |
| **响应式 UI** | 适配不同终端 | 桌面端 Tooltip，移动端点击详情。 |

### 4.2 业务规则
- **良率计算**: `Finished Yield = Π (Output_i / Input_i)`，即各关键工序良率的乘积。
- **默认值**: `Date Type=Weekly`, `Lot Type=HVM`, `Unit Type=NSQM`, `Project Type=Overall`。
- **交互规范**: 选中图表分段必须有视觉激活态（Active State）。

## 5. 非功能需求

- **性能**: 标准数据量下，图表刷新响应时间 < 3s。
- **可用性**: 遵循 AITC 色彩系统，支持键盘访问（Tab 键切换图例）。
- **兼容性**: 必须支持企业基线版本的 Chrome 和 Edge 浏览器。
- **健壮性**: 单个 API 失败不应导致整页白屏，需显示局部错误状态。

## 6. 高层架构设计

- **前端层**: 静态页面架构（HTML5, CSS3, 原生 JavaScript / jQuery, Bootstrap 5）。
- **后端层**: C# (ASP.NET Core API)，负责业务逻辑处理与数据聚合。
- **数据层**: SQLite (用于缓存汇总后的看板数据，提高查询效率)。
- **集成层**: 定时脚本从 QDMProductionDB (SQL Server) 抽取数据至本地 SQLite。

## 7. 模块职责划分

- **UI 模块**: 负责筛选栏渲染、ECharts/Chart.js 图表初始化及响应式布局。
- **API 模块**: 接收筛选参数，执行 SQL 查询，返回标准 JSON 数据契约。
- **计算引擎**: 实现批次级与周汇总良率的数学逻辑。
- **数据同步模块**: 每日/每周定时从源表（DS-01, DS-02）同步数据。

## 8. API 设计（草案）

### 8.1 获取筛选配置
- **GET** `/api/v1/filters`
- **返回**: 各筛选维度的可选值列表。

### 8.2 获取良率趋势数据
- **POST** `/api/v1/yield/trend`
- **参数**: `{ customer, plant, dateType, lotType, unitType, projectType }`
- **返回**: 时间序列数组，包含 Yield, Output, NSQM Loss。

### 8.3 获取缺陷分布数据
- **POST** `/api/v1/yield/defects`
- **参数**: `{ ...filters, topN: 20 }`
- **返回**: 缺陷代码、损失占比、责任部门分布。

## 9. 数据模型与数据库设计

## 9.1 候选表设计

#### 表 1: `Fact_FinishedLotYield` (对应 DS-01)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| ID | INTEGER | PK, AI | 自增主键 |
| ATSDate | DATETIME | Index | 统计日期 |
| DateType | TEXT | Index | Weekly/Monthly/Quarterly |
| Customer | TEXT | Index | 客户名称 |
| Plant | TEXT | Index | 工厂 |
| LotType | TEXT | - | 批次类型 (HVM等) |
| Yield | REAL | - | 良率值 |
| Output_NSQM | INTEGER | - | 产出数量 |

#### 表 2: `Fact_DefectLoss` (对应 DS-02)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| ID | INTEGER | PK, AI | 自增主键 |
| ATSDate | DATETIME | FK | 关联日期 |
| DefectCode | TEXT | Index | 缺陷代码 |
| DefectQty | INTEGER | - | 缺陷数量 |
| Department | TEXT | - | 责任部门 |
| LossRatio | REAL | - | 损失占比 |

### 9.2 数据约束与一致性
- **唯一约束**: `ATSDate + DateType + Customer + Plant + ProjectType` 构成逻辑唯一键。
- **审计字段**: 每张表包含 `LastUpdated` 时间戳。
- **敏感数据**: 涉及客户名称的数据在导出时需根据角色权限脱敏。

## 10. 关键流程 / 时序说明

1. **初始化**: 页面加载 -> 调用 `/filters` -> 设置默认值 -> 调用 `/yield/trend`。
2. **联动**: 用户切换 `Plant` -> 触发 `onFilterChange` -> 重新调用所有数据 API -> 图表 `setOption` 更新。
3. **下钻**: 点击 Pareto 柱状图 -> 获取 `DefectCode` -> 调用 `/yield/defect-detail` -> 更新右侧趋势图。

## 11. 安全、隐私与合规

- **身份验证**: 集成企业 Windows 身份验证 (AD)。
- **授权**: 导出功能仅限 `Manager` 和 `Yield Team` 角色。
- **合规**: 数据仅限内网访问，不存储任何个人身份信息 (PII)。

## 12. 可观测性与运维

- **日志**: 后端记录所有 API 请求耗时及异常堆栈。
- **监控**: 监控 SQLite 文件大小及数据同步脚本的执行状态。
- **健康检查**: `/api/health` 接口返回数据库连接状态。

## 13. 部署与环境规划

- **Web Server**: IIS 10+。
- **Runtime**: .NET 6/8 Runtime。
- **Database**: 随应用部署的 `App_Data/YieldDashboard.db` (SQLite)。
- **环境**: 开发 (DEV)、测试 (UAT)、生产 (PROD)。

## 14. 测试与验收方案

- **数据验证**: QA 需编写 SQL 对比 SQLite 与 QDMProductionDB 的聚合结果。
- **UI 验收**: 检查在 1366px (笔记本) 和 1920px (显示器) 下的布局适配。
- **交互验证**: 确认点击图表分段后，明细视图的切换延迟低于 500ms。

## 15. 风险、权衡与假设

- **假设**: 假设源表 DS-01/DS-02 的字段定义在开发期间不会发生重大变更。
- **权衡**: 使用 SQLite 替代实时连接 SQL Server 是为了保证看板的极速响应，但存在最高 24 小时的数据延迟。
- **风险**: 若业务方要求展示实时批次数据，当前的汇总表架构需重新设计。
