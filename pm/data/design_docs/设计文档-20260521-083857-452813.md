# 系统设计文档

> 该设计文档基于“中国象棋单机对战 Demo”的结构化需求生成。文档旨在指导研发团队完成从棋盘逻辑、数据持久化到视频化回放功能的完整开发。
> 收集覆盖率: 100% | 确认完成度: 100%

# 1. 范围与目标

- **项目名称**: 中国象棋单机对战 Demo
- **需求名称**: 中国象棋单机对战版需求规格说明
- **背景说明**: 开发一个支持本地双人同屏对战的中国象棋游戏，具备基础规则校验和对局回放功能。
- **目标**: 提供轻量级的本地对弈平台，支持严格的行棋规则校验，并能完整记录与视频化回放棋谱。

### 1.1 本次范围
- 单机双人同屏对战（红方先行）。
- 严格行棋规则校验：含马走日（蹩马腿）、象飞田（塞象眼/不过河）、士/将九宫格限制、兵过河限制、炮隔子打子。
- 胜负判定：手动吃掉对方“将/帅”判定胜利。
- 提和功能：一键提和，无需对方确认。
- 数据持久化：对局结束自动保存至 SQLite。
- 历史管理：展示对局列表（时间、步数、结果）。
- 视频化回放：支持播放/暂停、倍速切换（0.5x/1.0x/2.0x）、进度条跳转。

### 1.2 非本次范围
- 联网对战、AI 算法、悔棋功能、棋盘自动旋转、将军/自杀性行棋拦截。

## 2. 用户角色与参与方

- **本地玩家**: 在同一台设备上进行对弈的两名用户。
- **复盘者**: 需要回顾历史对局、分析行棋过程的用户。

## 3. 系统用例

### 3.1 用例：本地对弈
- **参与者**: 玩家 A（红）、玩家 B（黑）
- **触发条件**: 启动应用并进入对弈主页。
- **前置条件**: 棋盘初始化完成，红方先行。
- **主流程**:
    1. 玩家点击己方棋子，系统高亮合法落子点。
    2. 玩家点击目标位置，系统校验规则。
    3. 校验通过，棋子移动，若目标位有敌方棋子则执行“吃子”。
    4. 系统切换回合。
    5. 重复上述步骤直到一方吃掉对方“将/帅”。
- **验收检查点**: 违规移动必须被拦截；吃掉老将后必须停止对局并存档。

### 3.2 用例：视频化回放
- **参与者**: 复盘者
- **触发条件**: 在历史列表点击“查看回放”。
- **主流程**:
    1. 系统加载该局所有行棋记录。
    2. 棋盘恢复初始状态，开始按步序自动演示。
    3. 用户可随时点击暂停、调整倍速或拖动进度条。
- **验收检查点**: 棋子移动轨迹必须与原对局完全一致；进度条跳转需准确对应步数。

## 4. 功能需求

### 4.1 功能概述
系统需实现完整的象棋对弈逻辑、严格的路径校验、数据持久化及具备进度控制的回放系统。

### 4.2 功能明细
- **规则引擎**: 核心逻辑位于前端 JS，负责 7 种棋子的合法路径计算。
- **状态管理**: 记录当前回合、棋盘阵列状态、已吃棋子列表。
- **存档模块**: 后端 C# 接收对局结果及完整 Move List，写入 SQLite。

## 5. 非功能需求
- **响应性**: 本地操作延迟应小于 50ms。
- **易用性**: 回放界面需具备直观的视频控制感。
- **可靠性**: 即使浏览器关闭，已结束的对局数据也不得丢失。

## 6. 高层架构设计
采用**单体本地 Web 应用架构**：
- **前端**: 静态 HTML/CSS/JS，负责 UI 渲染与实时规则校验。
- **后端**: C# ASP.NET Core Minimal API，负责数据持久化与历史查询。
- **数据库**: SQLite (单文件)，存储于应用根目录。

## 7. 模块职责划分

- **UI Layer (HTML/CSS)**: 棋盘布局、历史列表、回放控制条。
- **Chess Engine (JS)**: 
    - `Validator`: 执行马走日、塞象眼等逻辑。
    - `Replayer`: 控制自动播放的时间轴与步序。
- **API Controller (C#)**: 处理 HTTP 请求，对接数据库。
- **Data Access (C#)**: 使用 Dapper 或 Entity Framework Core 访问 SQLite。

8. API 设计（草案）

| 接口名称 | 方法 | 路径 | 说明 |
| :--- | :--- | :--- | :--- |
| 保存对局 | POST | `/api/games` | 提交对局摘要及完整棋谱 |
| 获取列表 | GET | `/api/games` | 返回历史对局简报 |
| 获取详情 | GET | `/api/games/{id}` | 返回特定对局的完整步序 |

## 9. 数据模型与数据库设计

### 9.1 数据库表结构

## 表 1: `Games` (对局摘要)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| Id | INTEGER | PK, AI | 对局唯一标识 |
| StartTime | TEXT | NOT NULL | 开始时间 (ISO8601) |
| EndTime | TEXT | NOT NULL | 结束时间 |
| TotalSteps | INTEGER | NOT NULL | 总步数 |
| Result | TEXT | NOT NULL | 红胜/黑胜/和局 |

#### 表 2: `Moves` (行棋明细)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| Id | INTEGER | PK, AI | 记录 ID |
| GameId | INTEGER | FK (Games.Id) | 所属对局 |
| StepNum | INTEGER | NOT NULL | 步序 (1, 2, 3...) |
| Piece | TEXT | NOT NULL | 棋子类型 (如: R_MA) |
| FromX/Y | INTEGER | NOT NULL | 起始坐标 |
| ToX/Y | INTEGER | NOT NULL | 终点坐标 |
| EatPiece | TEXT | NULL | 被吃掉的棋子类型 |

### 9.2 数据约束
- `Moves` 表通过 `GameId` 与 `Games` 表保持级联删除关系。
- 索引建议：在 `Games.StartTime` 上建立降序索引，优化列表展示。

## 10. 关键流程 / 时序说明

### 10.1 对局结束存档流程
1. 前端检测到“老将被吃”或“点击提和”。
2. 前端锁定棋盘，整理 `MoveList` 数组。
3. 调用 `POST /api/games` 接口。
4. 后端开启事务，先插入 `Games` 表，再批量插入 `Moves` 表。
5. 事务提交，返回成功，前端跳转至历史列表。

## 11. 安全、隐私与合规
- **本地访问**: 仅监听 `localhost`，防止外部网络访问。
- **输入校验**: 后端需校验 `TotalSteps` 是否与 `Moves` 数量匹配，防止伪造数据。

## 12. 可观测性与运维
- **日志**: 后端记录每次 API 调用的耗时与异常信息。
- **数据库备份**: SQLite 文件可直接手动拷贝备份。

## 13. 部署与环境规划
- **运行环境**: .NET 6/7/8 Runtime。
- **部署方式**: 
    1. 编译 C# 程序为可执行文件。
    2. 运行后自动启动 Web 服务器。
    3. 用户通过浏览器访问 `http://localhost:5000`。

## 14. 测试与验收方案
- **规则测试**: 模拟“蹩马腿”和“象过河”场景，确认系统拦截。
- **胜负测试**: 模拟吃掉老将，确认 `Result` 记录为对应获胜方。
- **回放测试**: 调整倍速至 2.0x，确认动画播放流畅且步序无误。

## 15. 风险、权衡与假设
- **风险**: 不拦截自杀性行棋可能导致玩家误操作。
- **权衡**: 为了实现“手动吃将”的爽快感，牺牲了“将军”提醒逻辑，简化了开发复杂度。
- **假设**: 假设用户浏览器支持现代 JS (ES6+)。
