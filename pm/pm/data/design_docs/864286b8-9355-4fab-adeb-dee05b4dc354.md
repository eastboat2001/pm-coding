# 系统设计文档：课堂点名系统 (Demo 版)

## 1. 范围与目标
本项目旨在开发一个轻量级的课堂点名系统原型（MVP），通过数字化手段替代传统纸质点名。
- **核心目标**：实现教师发起签到、学生输入签到码自助签到的闭环流程。
- **适用场景**：线下课堂、讲座或小型会议。
- **非目标**：本 Demo 暂不考虑复杂的排课系统、教务系统对接及高并发下的性能优化。

## 2. 用户角色与参与方
| 角色 | 描述 |
| :--- | :--- |
| **教师 (Teacher)** | 发起签到任务，生成并分发签到码，查看签到统计结果。 |
| **学生 (Student)** | 在规定时间内输入签到码完成签到。 |

## 3. 系统用例

### UC1：教师发起签到
- **参与者**：教师
- **触发条件**：教师开始上课需要考勤。
- **前置条件**：教师已登录系统（Demo 版可简化为直接进入管理页）。
- **主流程**：
    1. 教师点击“开始签到”按钮。
    2. 系统生成一个随机的 4-6 位数字签到码。
    3. 系统创建一条签到记录（Session），状态为“进行中”。
    4. 教师将签到码口头或通过投影告知学生。
- **后置条件**：系统开始接收该签到码的请求。
- **验收检查点**：界面显示有效的签到码。

### UC2：学生自助签到
- **参与者**：学生
- **触发条件**：学生获取到教师提供的签到码。
- **前置条件**：学生访问签到页面。
- **主流程**：
    1. 学生输入姓名、学号。
    2. 学生输入签到码。
    3. 点击“提交签到”。
    4. 系统校验签到码有效性。
    5. 系统记录签到信息并提示成功。
- **备选/异常流程**：
    - 若签到码错误，提示“签到码无效”。
    - 若该学号已在当前 Session 签到，提示“请勿重复签到”。
- **后置条件**：数据库增加一条考勤记录。
- **验收检查点**：学生端显示“签到成功”，教师端可见该学生记录。

## 4. 功能需求
1. **签到管理**：教师生成签到码，手动开启/关闭签到。
2. **签到校验**：验证签到码的正确性及有效期。
3. **信息采集**：学生填写姓名、学号（基于 TBD 假设，暂定为手动填写）。
4. **结果展示**：教师端实时展示已签到人数及名单。

## 5. 非功能需求
1. **易用性**：学生端无需注册，扫码或输入 URL 即可使用。
2. **响应速度**：签到提交反馈应在 1 秒内完成。
3. **轻量化**：支持单机部署，资源占用低。

## 6. 高层架构设计
采用简单单体架构：
- **前端 (Frontend)**：Vue.js (SPA)，负责交互界面。
- **后端 (Backend)**：Flask (RESTful API)，负责业务逻辑处理。
- **数据库 (Database)**：SQLite，负责数据持久化。

## 7. 模块职责划分
- **Web UI (Vue)**：
    - `TeacherView`: 签到码生成页、实时名单展示页。
    - `StudentView`: 签到码输入表单。
- **API Service (Flask)**：
    - `SessionManager`: 负责签到码的生成、存储及状态控制。
    - `AttendanceManager`: 负责处理学生提交的签到数据。
- **Data Access (SQLAlchemy/SQLite)**：
    - 负责与 SQLite 数据库进行 CRUD 操作。

## 8. API 设计（草案）

| 接口路径 | 方法 | 说明 | 请求参数 |
| :--- | :--- | :--- | :--- |
| `/api/sessions` | POST | 教师创建签到任务 | `{ "title": "课程名称" }` |
| `/api/sessions/<id>` | GET | 获取特定签到任务详情 | - |
| `/api/checkin` | POST | 学生提交签到 | `{ "session_id": 1, "code": "1234", "student_name": "张三", "student_id": "202301" }` |
| `/api/sessions/<id>/records` | GET | 获取某次签到的所有学生名单 | - |

## 9. 数据模型与数据库设计

### 候选表/实体
1. **`checkin_session` (签到任务表)**
    - `id`: PK, Integer
    - `code`: String(6), 签到码
    - `status`: Integer (0: 关闭, 1: 开启)
    - `created_at`: DateTime
2. **`attendance_record` (考勤记录表)**
    - `id`: PK, Integer
    - `session_id`: FK (checkin_session.id)
    - `student_name`: String
    - `student_id`: String (学号)
    - `checkin_time`: DateTime

### 关系与基数
- 一个 `checkin_session` 对应多个 `attendance_record` (1:N)。

### 数据约束
- `(session_id, student_id)` 建立唯一索引，防止同一学生在同一次签到中重复提交。

## 10. 关键流程 / 时序说明
1. **教师端**：调用 `POST /api/sessions` -> 后端生成 `code` 并存入 SQLite -> 返回 `code` 给前端。
2. **学生端**：调用 `POST /api/checkin` -> 后端查询 `checkin_session` 表校验 `code` -> 校验通过则向 `attendance_record` 插入数据 -> 返回成功。

## 11. 安全、隐私与合规
- **Demo 级安全**：暂不实现复杂的 OAuth，教师端可使用简单的固定 Token 或 Session 保护。
- **数据隐私**：学号和姓名仅用于考勤展示，不存储敏感个人信息（如身份证、手机号）。

## 12. 可观测性与运维
- **日志**：Flask 打印标准请求日志，记录签到失败的尝试。
- **监控**：通过 SQLite 简单查询即可统计签到率。

## 13. 部署与环境规划
- **开发环境**：Python 3.9+, Node.js 16+。
- **部署方案**：
    - 后端：使用 `gunicorn` 或 Flask 自带服务器（仅限 Demo）。
    - 前端：`npm run build` 后由 Flask 托管静态文件或使用 Nginx。
    - 数据库：本地 `app.db` 文件。

## 14. 测试与验收方案
- **功能测试**：
    - 验证输入错误签到码是否被拦截。
    - 验证同一学号重复签到是否被拦截。
- **兼容性测试**：确保在手机浏览器上布局正常。

## 15. 风险、权衡与假设
- **风险**：学生可能将签到码发给未到场同学（代签）。
- **权衡**：为保持 Demo 简洁，暂不引入 GPS 地理围栏校验。
- **假设**：假设教师在课堂现场实时开启和关闭签到，以缩短签到码有效期。
