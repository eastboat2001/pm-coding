# 系统设计文档

## 1. 范围与目标

### 1.1 项目背景
本项目是一款为个人作品集设计的 3D 卡通风格竞速赛车游戏。旨在通过高完成度的视觉表现（卡通渲染）、核心操作手感（漂移喷气）以及完整的游戏逻辑（AI 橡皮筋机制、道具系统）展示开发者的综合技术实力。

### 1.2 目标
- 实现流畅的本地双人分屏对战体验。
- 构建具有竞争压力的 AI 系统。
- 演示完整的游戏生命周期管理（从菜单到结算）。

### 1.3 本次范围
- **核心玩法**：5个差异化角色、3条复杂 3D 赛道、3圈胜负制。
- **特色机制**：漂移喷气（Mini-Turbo）、随机道具（盲盒）、AI 橡皮筋、赛道救援。
- **表现层**：卡通渲染风格、分屏 HUD、动态音效系统。

### 1.4 非本次范围
- 历史记录持久化存储。
- 联网对战功能。
- 复杂的杯赛/大奖赛积分系统。

---

## 2. 用户角色与参与方
- **玩家 1 (P1)**：使用键盘左侧（WASD + Space）进行操作。
- **玩家 2 (P2)**：使用键盘右侧（方向键 + Enter）进行操作。
- **AI 竞争对手**：由系统控制，根据玩家表现动态调整难度。
- **招聘官/观众**：通过观察游戏运行效果评估开发者技术水平。

---

## 3. 系统用例

### 用例 1：本地分屏竞速对战
- **参与者**：P1, P2, AI
- **触发条件**：在选择界面确认角色与赛道后加载比赛。
- **前置条件**：系统已加载选定的赛道资源与角色模型。
- **主流程**：
    1. 倒计时结束，玩家通过键盘控制赛车前进。
    2. 玩家通过漂移积累 Mini-Turbo 并在释放时获得加速。
    3. 玩家撞击盲盒，系统根据排名分配道具。
    4. 玩家使用道具干扰对手或强化自身。
    5. AI 根据橡皮筋机制实时调整速度，保持与玩家的距离。
- **备选/异常流程**：
    - 赛车掉出赛道：触发救援系统，扣除道具并复位至最近检查点。
    - 碰撞障碍物：赛车减速并播放碰撞音效。
- **后置条件**：记录玩家到达终点的顺序。
- **验收检查点**：分屏渲染无明显掉帧，双人操作互不干扰。

## 4. 功能需求
详见 PRD 结构化摘要，重点实现：
- **漂移系统**：蓝/红火花分级蓄力逻辑。
- **道具系统**：基于排名的概率权重算法。
- **AI 系统**：基于路径点（Waypoints）的寻路与速度修正。

---

## 5. 非功能需求
- **响应性**：键盘输入到赛车动作的延迟需低于 16ms（60fps）。
- **性能**：在主流浏览器中保持 60fps，分屏状态下 Draw Calls 需严格控制。
- **易用性**：主菜单支持纯键盘操作。

---

## 6. 高层架构设计
采用**单体架构**，前端负责核心逻辑与渲染，后端负责配置分发。

- **前端 (Web 3D)**：负责渲染（Three.js/Babylon.js 选型 TBD）、物理模拟、UI 交互、音效播放。
- **后端 (C#)**：提供轻量级 REST API，用于初始化游戏配置（角色属性、赛道参数）。
- **数据库 (SQLite)**：存储静态配置数据。

---

## 7. 模块职责划分

| 模块名称 | 职责描述 |
| :--- | :--- |
| **GameCore** | 状态机管理（Loading, Racing, Paused, Finished）。 |
| **InputManager** | 监听并分发 P1/P2 的键盘事件，处理按键冲突。 |
| **VehiclePhysics** | 处理赛车移动、漂移、碰撞反馈及地形减速逻辑。 |
| **AISystem** | 执行橡皮筋算法，控制 AI 赛车的路径跟随与速度。 |
| **ItemSystem** | 道具盲盒触发、道具抽取算法、道具效果执行。 |
| **ViewManager** | 处理分屏渲染逻辑、HUD 更新、小地图坐标映射。 |
| **AudioManager** | 动态引擎声合成、3D 空间音效、背景音乐切换。 |

# 9. 数据模型与数据库设计

### 9.1 候选表设计 (SQLite)

#### 表：Characters (角色属性)
| 字段 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| ID | INTEGER | PK | 唯一标识 |
| Name | TEXT | NOT NULL | 角色名称 |
| MaxSpeed | FLOAT | - | 最高时速 |
| Acceleration | FLOAT | - | 加速度 |
| Handling | FLOAT | - | 转向灵活性 |
| Weight | FLOAT | - | 重量（抗撞击能力） |

#### 表：Tracks (赛道信息)
| 字段 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| ID | INTEGER | PK | 唯一标识 |
| Name | TEXT | NOT NULL | 赛道名称 |
| Difficulty | INTEGER | - | 难度等级 (1-5) |
| AssetPath | TEXT | - | 3D 模型资源路径 |

### 9.2 数据约束与一致性
- 角色属性值范围定义在 0-100 之间。
- 赛道资源路径必须指向有效的静态资源目录。

## 10. 关键流程 / 时序说明

### 10.1 道具获取流程
1. **触发**：赛车 Collider 与盲盒 Collider 发生 Trigger 事件。
2. **计算**：前端向逻辑层请求道具，逻辑层根据 `CurrentRank` 计算概率区间。
3. **反馈**：HUD 播放滚动动画，最终停留在选定道具图标。
4. **执行**：玩家按下触发键，根据道具类型（追踪/放置/强化）生成对应的 GameObject 或修改赛车状态。

## 11. 安全、隐私与合规
- **本地运行**：不涉及用户个人隐私数据采集。
- **合规性**：美术资源需确保无版权争议（建议使用自制或开源授权资源）。

---

## 12. 可观测性与运维
- **前端日志**：在控制台输出关键逻辑日志（如：`Lap 1 Completed`, `Item Spawned: Missile`）。
- **性能监控**：集成 `stats.js` 实时监控 FPS 和内存占用。

---

## 13. 部署与环境规划
- **开发环境**：Visual Studio 2022 (C#) + VS Code (Frontend)。
- **托管方案**：后端使用 Kestrel 本地运行，前端通过静态文件服务器托管。
- **数据库**：项目根目录下的 `game_config.db`。

---

## 14. 测试与验收方案
- **冒烟测试**：启动游戏，确保能进入第一条赛道并看到分屏。
- **功能测试**：
    - 验证 P1/P2 同时按下按键时无操作丢失。
    - 验证掉出赛道后 3 秒内完成救援复位。
- **性能测试**：在分屏模式下，AI 赛车满载（如 6 名 AI）时帧率不低于 50fps。

---

## 15. 风险、权衡与假设
- **风险**：Web 环境下的多键位冲突（Ghosting）。
- **权衡**：为了 Demo 的轻量化，放弃了复杂的物理引擎（如 Ammo.js），改用简化的射线检测（Raycast）处理赛车与地面的关系。
- **假设**：假设用户使用的浏览器支持 WebGL 2.0。
