## 1. 范围与目标

- **项目名称**: ABF良率分析系统
- **需求名称**: 缺陷根因追溯与跨站点数据关联需求
- **背景说明**: ABF 载板制造工艺复杂，涉及多个生产站点。目前工程师在追溯缺陷根因时，需手动从不同系统（如 MES、EAP）导出 Excel 并进行人工关联，效率极低。
- **目标**: 
    - 实现跨站点生产数据的自动化聚合。
    - 将根因追溯的耗时从“小时级”降低至“分钟级”。
- **本次范围**: 
    - 跨站点批次（Lot）数据自动关联引擎。
    - 基础数据查询与展示界面。
- **非本次范围**: 
    - 自动根因诊断算法（AI/ML 部分）。
    - 实时生产告警推送。

## 2. 用户角色与参与方

| 角色 | 职责描述 |
| :--- | :--- |
| **工艺工程师 (PE)** | 核心用户。负责分析良率波动，通过系统追溯特定批次在各站点的工艺参数。 |
| **质量工程师 (QE)** | 核心用户。负责缺陷模式分析，评估跨站点的质量一致性。 |

## 3. 系统用例

### 用例 UC-01: 跨站点批次追溯分析
- **参与者**: 工艺工程师、质量工程师
- **触发条件**: 发现成品良率异常或特定批次出现集中性缺陷。
- **前置条件**: 
    - 工程师已登录系统。
    - 原始生产数据已从 MES/EAP 等系统同步至本系统或可实时访问。
- **主流程**:
    1. 工程师在搜索框输入目标 **批次号 (Lot ID)**。
    2. 系统验证批次号合法性。
    3. 系统检索该批次经过的所有 **生产站点 (Stations)**。
    4. 系统根据预设的关联逻辑，自动聚合各站点的：生产时间、操作员、设备 ID、工艺参数、缺陷检测结果。
    5. 系统生成并展示“跨站点生产全景视图”。
- **备选/异常流程**:
    - **批次号不存在**: 系统提示错误，建议检查输入。
    - **数据缺失**: 若某站点数据未同步，系统在对应环节标记“数据缺失”而非中断流程。
- **后置条件**: 系统记录本次查询日志，供后续审计。
- **验收检查点**:
    - [ ] 输入 Lot ID 后，能否在 5 秒内展示至少 3 个站点的关联数据？
    - [ ] 关联数据是否包含该批次在各站点的进出站时间？

## 4. 功能需求

## 4.1 功能明细
- **F01: 批次全生命周期关联**: 自动识别 Lot 在 A 站、B 站、C 站的流转记录。
- **F02: 缺陷数据聚合**: 将 AOI/AVI 检测到的缺陷信息与生产批次在各站点的工艺状态挂钩。
- **F03: 基础查询界面**: 提供基于 Lot ID 的一键式查询入口。

### 4.2 业务规则
- **R01 (TBD)**: 批次号转换规则。若 Lot 在某站点发生拆分（Split）或合并（Merge），系统需支持父子批次的追溯逻辑。

 5. 非功能需求

- **性能**: 跨站点数据关联查询响应时间 < 5s。
- **可用性**: 系统需支持 7x24 小时运行，以配合产线排班。
- **准确性**: 关联准确率必须达到 100%（基于原始系统提供的 ID）。

## 6. 高层架构设计

系统采用前后端分离架构：
- **前端**: 静态页面（HTML/CSS/原生 JavaScript），负责数据呈现与交互。
- **后端**: C# (ASP.NET Core / .NET 6+)，负责业务逻辑处理与数据聚合。
- **数据库**: SQLite，用于存储配置信息、站点映射关系及部分缓存数据。

## 7. 模块职责划分

| 模块名称 | 职责描述 |
| :--- | :--- |
| **Data Ingestion (接入层)** | 负责从 MES/EAP 等外部系统拉取或接收原始数据。 |
| **Correlation Engine (关联引擎)** | 核心逻辑层。负责根据 Lot ID/Panel ID 进行跨表/跨库关联。 |
| **Query API (查询接口)** | 提供 RESTful 接口供前端调用。 |
| **UI Layer (展示层)** | 展示批次流转时间轴、工艺参数对比表等。 |

## 9. 数据模型与数据库设计

### 9.1 候选表设计

#### 表 1: `Dim_Station` (站点维度表)
- `StationID` (PK, Integer): 站点唯一标识
- `StationName` (String): 站点名称（如：曝光、显影、电镀）
- `SourceSystem` (String): 数据来源系统（MES/EAP）

#### 表 2: `Fact_ProductionRecord` (生产事实表)
- `RecordID` (PK, Integer): 记录唯一标识
- `LotID` (Index, String): 批次号
- `PanelID` (Index, String, Optional): 大板号 (TBD)
- `StationID` (FK, Integer): 关联站点
- `EquipmentID` (String): 设备编号
- `InTime` (DateTime): 进站时间
- `OutTime` (DateTime): 出站时间

#### 表 3: `Fact_DefectRecord` (缺陷事实表)
- `DefectID` (PK, Integer)
- `LotID` (FK, String)
- `StationID` (FK, Integer)
- `DefectCode` (String): 缺陷代码
- `Count` (Integer): 缺陷数量

### 9.2 数据约束与一致性
- `LotID` 在 `Fact_ProductionRecord` 中不唯一（一个批次对应多个站点）。
- 建议对 `LotID` 建立索引以优化查询速度。

## 10. 关键流程 / 时序说明

1. 用户在前端输入 `LotID`。
2. 后端接收请求，首先查询 `Fact_ProductionRecord` 获取该批次的所有站点记录。
3. 后端并行查询 `Fact_DefectRecord` 获取各站点的缺陷分布。
4. 后端根据 `InTime` 对站点记录进行排序，构建生产链路。
5. 返回 JSON 数据至前端进行渲染。

## 11. 安全、隐私与合规

- **数据脱敏**: 界面不显示操作员的敏感个人信息（如手机号）。
- **访问控制**: 仅限内网访问，需对接厂区统一身份认证系统。

## 12. 可观测性与运维

- **日志记录**: 记录所有查询请求的耗时及失败原因。
- **健康检查**: 提供 `/health` 接口监控后端服务状态。

## 13. 部署与环境规划

- **数据库**: 使用 SQLite，数据库文件存放于服务器本地持久化目录。
- **后端**: 部署为 Windows Service 或 Docker 容器。

## 14. 测试与验收方案

- **单元测试**: 验证关联引擎在处理“批次拆分”逻辑时的正确性。
- **集成测试**: 模拟从 MES 导入 1000 条记录，验证查询响应时间。
- **UAT 验收**: 工程师随机抽取 5 个批次，对比系统自动关联结果与人工 Excel 关联结果的一致性。

## 15. 风险、权衡与假设

- **假设**: 假设所有站点的 MES 数据中 `LotID` 命名规范是一致的。
- **风险**: 若不同站点间存在复杂的批次重命名逻辑，自动关联可能会失效。
- **权衡**: 初期采用 SQLite 以简化部署，若未来数据量超过千万级，需考虑迁移至 PostgreSQL 或 SQL Server。
