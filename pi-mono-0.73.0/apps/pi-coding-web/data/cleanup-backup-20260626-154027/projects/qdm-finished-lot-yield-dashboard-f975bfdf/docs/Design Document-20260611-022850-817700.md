## 1. Scope and Objectives

- **Project Name:** D.CHQ.QDM Finished Lot Yield Dashboard
- **Requirement Name:** Finished Lot Performance Overview and Defect Loss Ratio Dashboard
- **Background:** The dashboard provides high-level views of current key yield metrics for different products in the factory. It is updated by an automated scheduled script every day so QDM and yield teams can review current finished-lot performance without manual report preparation.
- **Objective:** Drive yield improvement, reduce production costs, and increase output by exposing overall yield trends, drill-down segments, product views, loss-code Pareto, loss-operation attribution, and root-cause ownership.

### 1.1 In Scope
- **Finished Lot Performance Overview Trend:** Weekly finished yield, latest-week Output, Yield, and NSQM Loss.
- **Loss Ratio By Defect Code:** Top 10-20 defect loss ratios, defect-code trend, and cause department distribution.
- **Unified Filters:** Customer, Plant, Date Type, Lot Type, Unit Type, and Project Type.
- **Calculation Logic:** Finished Yield calculation for lot-level and weekly aggregated product yield.
- **UI/UX:** Responsive layout, interactive charts, and export functionality.

### 1.2 Out of Scope
- Automated process-parameter optimization.
- Formal QMS defect disposition workflow replacement.
- Supplier or customer complaint management.
- Self-service BI modeling beyond the approved chart inventory.

## 3. System Use Cases

### 3.1 UC-01: Review Weekly Yield Performance
- **Actor:** Yield Team / Manager
- **Trigger:** User opens the dashboard.
- **Preconditions:** Data has been synced to the local SQLite database.
- **Main Flow:**
    1. User navigates to the "Finished Lot Performance Overview Trend" page.
    2. System loads default filters (Weekly, HVM, NSQM, Overall).
    3. System displays the Yield Trend line chart and latest-week KPI cards.
- **Postconditions:** User has a clear view of current yield health.
- **Acceptance Checks:** Yield values match DS-01 source data.

### 3.2 UC-02: Drill-down into Specific Time Segments
- **Actor:** Engineer
- **Trigger:** User clicks a data point on the trend chart.
- **Preconditions:** Trend chart is rendered.
- **Main Flow:**
    1. User clicks a specific week on the line chart.
    2. The right-side detail panel refreshes to show specific Output, Yield, and NSQM Loss for that week.
- **Postconditions:** Detail panel reflects the selected week's context.

## 3.3 UC-03: Analyze Defect Pareto
- **Actor:** Manager / Engineer
- **Trigger:** User navigates to "Loss Ratio By Defect Code" page.
- **Main Flow:**
    1. System displays a Pareto chart of top 10-20 defect codes.
    2. User selects a defect code.
    3. Right-side charts update to show the trend for that specific defect and the department distribution.
- **Acceptance Checks:** Pareto ranking is correct based on Loss Ratio.

## 4. Functional Requirements

### 4.1 Feature Details
- **Unified Filter Bar:** Shared across all pages. Supports multi-select for Customer and Plant.
- **Interactive Charts:** Clicking segments in the "Hero" chart (left) must update the "Detail" charts (right).
- **Yield Calculation Engine:** 
    - Lot Yield = $\prod (Process Output / Process Input)$
    - Weekly Yield = Aggregated weekly shipment/finished output basis.
- **Data Export:** Export current view data to CSV/Excel, including the active filter context in the header/filename.

## 5. Non-Functional Requirements

- **Performance:** Dashboard charts should render within 3 seconds for standard data volumes.
- **Responsiveness:** Support Desktop (1920x1080), Tablet, and Mobile widths using Bootstrap.
- **Availability:** Data is updated daily via automated script; dashboard must show "Last Updated" timestamp.
- **Accessibility:** Keyboard navigation for legends and tooltips; high-contrast color palette (AITC standard).

## 6. High-Level Architecture

The system follows a standard 3-tier architecture using the specified technology stack:

- **Frontend:** Static HTML5, CSS3 (Bootstrap), and Vanilla JavaScript/jQuery. Communicates with the backend via AJAX/Fetch.
- **Backend:** C# (ASP.NET Core Web API) providing RESTful endpoints.
- **Database:** SQLite for local data storage and fast query performance for the dashboard.

## 7. Module Responsibilities

- **Web UI (Frontend):** Handles routing between pages, filter state management, and Chart.js/ECharts rendering.
- **API Service (Backend):** Handles filter logic, data aggregation, and calculation of yield metrics.
- **Data Access Layer:** Executes SQL queries against SQLite.
- **Sync Service (External/TBD):** Automated script that populates SQLite from QDMProductionDB.

## 8. API Design (Draft)

| Endpoint | Method | Description |
| :--- | :--- | :--- |
| `/api/filters` | GET | Returns available options for Customer, Plant, etc. |
| `/api/yield/summary` | GET | Returns trend data and KPI cards based on filters. |
| `/api/yield/defects` | GET | Returns Pareto data for defect codes. |
| `/api/yield/details` | GET | Returns drill-down data for a specific selection. |

## 9. Data Model and Database Design

### 9.1 Candidate Tables

#### Table: `FinishedLotSummary` (Maps to DS-01)
- `Id`: INTEGER (PK)
- `ATSDate`: DATETIME (Index)
- `DateType`: TEXT (Weekly/Quarterly/Monthly)
- `Customer`: TEXT
- `Plant`: TEXT
- `LotType`: TEXT
- `UnitType`: TEXT
- `ProjectType`: TEXT
- `Yield`: REAL
- `Output_NSQM`: INTEGER
- `Input_Qty`: INTEGER

#### Table: `DefectSummary` (Maps to DS-02)
- `Id`: INTEGER (PK)
- `ATSDate`: DATETIME
- `DefectCode`: TEXT (Index)
- `DefectQty`: INTEGER
- `LossRatio`: REAL
- `Department`: TEXT
- `Customer`: TEXT
- `Plant`: TEXT

### 9.2 Data Constraints
- `ATSDate` + `Customer` + `Plant` + `LotType` + `DateType` should be unique for summary records.
- Retention: Keep 2 years of historical data in SQLite; older data archived.

## 10. Key Workflows / Sequence Narratives

1. **Initialization:** Frontend requests `/api/filters` -> Populates dropdowns with defaults.
2. **Data Fetch:** Frontend requests `/api/yield/summary?dateType=Weekly&lotType=HVM...` -> Backend queries SQLite -> Returns JSON.
3. **Interaction:** User clicks "Defect A" in Pareto -> Frontend triggers local filter or API call for `/api/yield/details?defectCode=A` -> Right-side charts refresh.

## 11. Security, Privacy, and Compliance

- **Authentication:** Integrated with corporate SSO (TBD).
- **Data Privacy:** No PII (Personally Identifiable Information) is stored. Data is strictly manufacturing metrics.
- **Export Control:** Export button visibility controlled by user role (Yield Team/Manager only).

## 12. Observability and Operations

- **Logging:** Backend logs API request duration and errors to a local file or Serilog.
- **Data Freshness:** A "Data Last Updated" label must be visible on the dashboard footer.
- **Health Check:** Simple `/api/health` endpoint to verify SQLite connection.

## 13. Deployment and Environment Plan

- **Environment:** Development, UAT, and Production.
- **Hosting:** Windows Server with IIS for the C# Web API and static file hosting.
- **Database:** `qdm_yield.db` (SQLite file) located in the App_Data folder.

## 14. Testing and Acceptance Plan

- **Unit Testing:** C# calculation logic for Yield.
- **Data Validation:** Compare SQLite `SUM(Output_NSQM)` against `QDMProductionDB` source for the same period.
- **UI Testing:** Verify responsiveness on Chrome and Edge.
- **Acceptance:** Yield team signs off on the "Latest-week" KPI accuracy.

## 15. Risks, Trade-offs, and Assumptions

- **Assumption:** The automated script for data sync is handled externally or as a separate task.
- **Risk:** SQLite performance might degrade if the "DefectSummary" table grows too large without proper indexing.
- **Trade-off:** Using Vanilla JS instead of a framework (React/Vue) simplifies deployment but requires more manual DOM manipulation for complex interactions.
