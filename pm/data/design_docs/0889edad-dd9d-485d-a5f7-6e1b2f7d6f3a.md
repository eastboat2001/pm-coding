# 系统设计文档

> 该设计文档基于已收集的 100% 需求信息整理而成。系统定位为轻量级个人本地工具，采用单体架构实现。

## 1. 范围与目标

- **项目名称**: 个人记账系统 (Personal Ledger Demo)
- **背景说明**: 针对个人日常消费设计的轻量级本地记账工具，解决用户记录收支、分类统计及财务状况复盘的需求。
- **目标**: 提供一个无需联网、私密性强、操作简便的 PC 端记账界面，支持完整的收支生命周期管理。

### 1.1 本次范围
- **核心 CRUD**: 收支记录的新增、编辑、删除、查询。
- **配置管理**: 自定义收支分类（支持收支隔离）及支付方式标签。
- **筛选统计**: 按月份、按分类筛选，并实时联动汇总总收入、总支出及结余。
- **本地化**: 基于 SQLite 的本地数据持久化。

### 1.2 非本次范围
- 多用户登录与权限管理。
- 复杂统计图表（饼图、趋势图等）。
- 自动化功能（账单导入、自动对账）。
- 附件/图片上传。
- 导出 Excel/CSV 功能。

## 2. 用户角色与参与方
- **个人用户**: 系统唯一使用者，拥有对所有数据和配置的完全控制权。

## 3. 系统用例

### 3.1 用例：记录一笔新的收支
- **参与者**: 个人用户
- **触发条件**: 用户点击“新增记录”按钮。
- **前置条件**: 系统已正常启动，数据库连接正常。
- **主流程**:
    1. 用户选择账目类型（收入 或 支出）。
    2. 系统根据类型自动过滤并展示对应的分类下拉列表。
    3. 用户输入金额（必填，支持两位小数）。
    4. 用户确认日期（默认为当天，可修改）。
    5. 用户选填分类、支付方式及备注。
    6. 用户点击提交。
- **备选/异常流程**:
    - 若金额未填写或格式错误，系统提示“请输入有效的金额”。
    - 若未选择账目类型，提交按钮禁用或报错。
- **后置条件**: 数据存入数据库，主列表自动刷新并按日期倒序排列。
- **验收检查点**: 列表顶部汇总金额随之更新。

### 3.2 用例：按维度筛选并查看汇总
- **参与者**: 个人用户
- **触发条件**: 用户切换月份下拉框或分类下拉框。
- **前置条件**: 存在历史账目数据。
- **主流程**:
    1. 用户在主界面选择“2023-10”月份。
    2. 用户选择“餐饮”分类。
    3. 系统实时过滤列表，仅展示符合条件的记录。
    4. 系统重新计算当前筛选结果下的“总收入”、“总支出”和“结余”。
- **验收检查点**: 汇总值必须等于当前可见列表记录的代数和。

### 3.3 用例：管理配置项（分类/支付方式）
- **参与者**: 个人用户
- **触发条件**: 用户进入配置管理页面。
- **主流程**:
    1. 用户添加一个新的支出分类“宠物”。
    2. 用户尝试删除一个已有关联账目的分类“餐饮”。
- **备选/异常流程**:
    - 系统检测到“餐饮”分类下已有账目，拦截删除请求并提示“该分类已被使用，无法删除”。
- **验收检查点**: 已引用的配置项删除按钮应置灰或点击后弹出明确拦截提示。

## 4. 功能需求
- **F01: 收支录入**: 支持类型、金额、日期、分类、支付方式、备注的录入。
- **F02: 记录维护**: 支持对已有记录的编辑修改和物理删除。
- **F03: 配置项管理**: 维护分类表（区分收支）和支付方式表。
- **F04: 实时统计**: 筛选条件下自动计算 `Sum(Income)`, `Sum(Expense)`, `Balance`。

## 5. 非功能需求
- **易用性**: 适配 PC 浏览器，支持长页面滚动，不设分页。
- **性能**: 本地单机运行，列表加载时间应小于 200ms。
- **私密性**: 数据存储于本地 `ledger.db` 文件，不进行网络同步。
- **数据一致性**: 严格执行外键约束，防止孤儿数据。

## 6. 高层架构设计
系统采用经典的 **单体架构 (Monolithic)**，前后端分离开发，本地部署。
- **前端 (Vue.js)**: 负责 UI 渲染、筛选逻辑触发及基础校验。
- **后端 (Flask)**: 提供 RESTful API，处理业务逻辑及数据库交互。
- **数据库 (SQLite)**: 单文件数据库，存储所有配置和账目。

## 7. 模块职责划分
- **Web UI (Vue)**: 
    - `RecordModule`: 负责账目列表展示及 CRUD 弹窗。
    - `FilterModule`: 负责月份和分类的联动筛选。
    - `ConfigModule`: 负责分类和支付方式的增删。
- **API Service (Flask)**:
    - `RecordController`: 处理账目增删改查请求。
    - `ConfigController`: 处理配置项校验与持久化。
    - `StatService`: 负责根据条件计算汇总金额。
- **Data Access (SQLAlchemy/SQLite)**: 负责实体映射与 SQL 执行。

## 8. API 设计（草案）

| 接口路径 | 方法 | 说明 |
| :--- | :--- | :--- |
| `/api/records` | GET | 获取账目列表（支持 month, category_id 过滤） |
| `/api/records` | POST | 新增账目 |
| `/api/records/<id>` | PUT | 修改账目 |
| `/api/records/<id>` | DELETE | 删除账目 |
| `/api/categories` | GET | 获取分类列表（支持 type 过滤） |
| `/api/categories` | POST | 新增分类 |
| `/api/payment-methods` | GET | 获取支付方式列表 |

## 9. 数据模型与数据库设计

### 9.1 实体关系图 (ERD) 逻辑
- `Record` (N) -> (1) `Category` (可选)
- `Record` (N) -> (1) `PaymentMethod` (可选)

### 9.2 数据库表设计 (SQLite)

#### 表 1: `categories` (分类表)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| id | INTEGER | PK, AI | 唯一标识 |
| name | TEXT | NOT NULL | 分类名称 |
| type | TEXT | CHECK(type IN ('income', 'expense')) | 收入或支出类型 |

#### 表 2: `payment_methods` (支付方式表)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| id | INTEGER | PK, AI | 唯一标识 |
| name | TEXT | NOT NULL | 支付方式名称（如：微信、支付宝） |

#### 表 3: `records` (账目记录表)
| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| id | INTEGER | PK, AI | 唯一标识 |
| type | TEXT | NOT NULL | income / expense |
| amount | REAL | NOT NULL | 金额（存储为浮点数，前端保留2位） |
| date | TEXT | NOT NULL | 日期（ISO8601 格式: YYYY-MM-DD） |
| category_id | INTEGER | FK (categories.id) | 关联分类，可为 NULL |
| method_id | INTEGER | FK (payment_methods.id) | 关联支付方式，可为 NULL |
| note | TEXT | - | 备注 |

### 9.3 数据约束与一致性
- **删除保护**: 在 `categories` 和 `payment_methods` 删除前，必须查询 `records` 表是否存在关联 ID。若存在，后端返回 403 错误。
- **索引建议**: 对 `records.date` 建立索引以优化倒序排列性能。

## 10. 关键流程 / 时序说明
1. **初始化**: 前端挂载后，并发请求 `categories`、`payment_methods` 和 `records`（无筛选）。
2. **联动筛选**: 用户选择月份 -> 前端更新 state -> 触发 `fetchRecords(month, category)` -> 后端执行 `SELECT ... WHERE date LIKE 'YYYY-MM%'` -> 返回数据 -> 前端计算 `reduce` 得到汇总值。

## 11. 安全、隐私与合规
- **数据隐私**: 数据完全存储在用户本地，不上传云端。
- **输入校验**: 后端对 `amount` 进行数值校验，防止 SQL 注入（使用 ORM）。

## 12. 可观测性与运维
- **日志**: Flask 开启基础文件日志，记录 API 报错信息。
- **备份**: 建议用户手动备份 `instance/ledger.db` 文件。

## 13. 部署与环境规划
- **开发环境**: Python 3.9+, Node.js 16+。
- **运行环境**: 
    - 后端：`python app.py` (Flask 内置服务器，本地访问)。
    - 前端：`npm run build` 后由 Flask 托管静态文件，或独立运行。

## 14. 测试与验收方案
- **功能测试**: 验证金额 `100.55` 录入后显示是否正确。
- **边界测试**: 验证删除已引用的分类是否被拦截。
- **逻辑测试**: 验证“结余”是否等于 `总收入 - 总支出`。

# 15. 风险、权衡与假设
- **假设**: 用户单机使用，不考虑多端同步。
- **权衡**: 放弃分页以换取更直观的滚动体验，在数据量超过万条时可能存在渲染压力（对于个人记账，预计 5-10 年内不会达到此瓶颈）。

## 16. 里程碑与交付计划
- **M1**: 数据库设计与 Flask 基础 CRUD API 完成。
- **M2**: Vue 基础界面与录入功能完成。
- **M3**: 筛选与统计逻辑联调。
- **M4**: 配置管理与引用保护逻辑完善。
