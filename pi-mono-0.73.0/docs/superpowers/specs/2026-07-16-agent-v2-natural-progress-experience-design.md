# Agent V2 自然对话与动态进度融合设计

## 背景

PI Coding Web 的应用生成模式当前把 Agent V2 的任务、产物、校验、诊断、输出和交付事件逐条投影为独立状态卡片。由于任务状态更新以带时间戳的新消息追加，同一任务的 `pending`、`failed`、`succeeded` 会同时留在会话中。用户看到的是不断增长的技术状态列表，而不是一个正在持续推进的应用生成过程。

旧版界面具有更自然的交互节奏：Agent 会用连续文字说明已经读取什么、理解了什么、准备做什么和检查结果，工具调用只是穿插其中的执行证据。它的问题是工具卡、Skill 加载和资源读取也会逐条堆积，缺少统一进度和明确的展开管理。

本设计融合两者的优点：自然对话作为主体验，单一动态进度卡提供可信的结构化状态，技术过程按需展开，最终应用通过 URL 在新网页打开，不在当前页面嵌入实时预览。

## 目标

- 恢复类似旧版的自然、连续、可流式阅读的 Agent 对话体验。
- 每次应用生成只显示一个可原位更新的动态进度卡，不再产生状态卡片墙。
- 让用户随时知道当前阶段、当前动作、已完成工作和是否仍在运行。
- 将文件、工具、Skill、校验、诊断等技术事件聚合为按需展开的执行证据。
- 统一页面级面板、会话卡片和卡片内部详情的展开状态，避免覆盖、争抢空间和互相矛盾。
- 失败、修复和重新校验继续更新同一运行视图，不保留误导性的过期当前状态。
- 完成后提供清晰的交付摘要和新窗口访问 URL。
- 保持历史会话可恢复、可审计，并保留原始事件作为诊断依据。

## 非目标

- 不在对话页面内嵌应用实时预览。
- 不展示模型私有推理过程或 chain-of-thought。
- 不把每个底层事件转换成一条聊天消息。
- 不使用虚假的完成百分比或没有依据的剩余时间预测。
- 不删除底层 Agent V2 事件、诊断或持久化记录。
- 不改变 Chat 模式的普通对话交互。

## 设计原则

### 自然对话主导

应用生成模式仍然是一段对话。Agent 应在开始、重要成果、校验、修复和交付等关键节点，用简短自然语言说明正在做什么。结构化状态服务于对话，而不是取代对话。

### 一个运行，一个展示实体

每个 `runId` 对应一个动态进度实体。任务、校验和产物状态按稳定标识原位更新；时间戳只属于事件历史，不参与用户可见实体的身份。

### 过程可见，细节克制

用户默认看到业务可理解的阶段和动作。文件路径、校验 ID、checksum、Skill 资源和诊断代码只在详细过程里展示。

### 展开按区域互斥

同一视觉区域内只允许一个占用型内容展开。桌面端互不覆盖的侧栏和会话详情可以共存；移动端共享同一空间时必须互斥。弹窗始终拥有最高优先级。

### 状态来自真实事件

进度和行动说明必须由真实任务阶段、模型输出或工具事件驱动。没有新进展时可以显示持续运行时间，但不能制造虚假步骤。

## 最终体验

### 1. 启动

用户提交应用生成请求后，Agent 立即开始一段自然文字响应：

> 好的，我会先整理页面结构和核心玩法，然后实现键盘与触屏控制，最后检查生成结果。

第一段文字开始输出时创建动态进度卡。卡片以紧凑状态显示：

- `正在生成应用`
- 当前阶段，例如 `实现 · 第 2/5 阶段`
- 当前动作，例如 `正在创建游戏逻辑和触屏控制`
- 已运行时间
- 状态图标和展开按钮

### 2. 执行

Agent 只在有意义的里程碑追加自然说明：

> 基础玩法已经完成。接下来我会补充计分、重新开始和移动端控制。

动态进度卡同步原位更新阶段、动作和完成项。连续的文件读取、任务更新和资源加载不会产生新的顶层卡片。

### 运行卡的位置和生命周期

运行中的动态进度卡位于消息列表与输入框之间的独立运行槽中，沿用旧版 `Preview ready` 状态条所在的视觉位置。它参与正常页面布局并始终可见，不使用覆盖消息或输入框的浮层。

自然语言行动说明继续追加到消息列表。运行槽只渲染当前活动运行；同一会话如果不允许并行生成，就不会同时出现多个活动卡。卡片展开时向消息区域占用空间，并相应缩小消息列表可视高度，输入框位置保持稳定。

运行结束后，活动槽中的卡片被移除，并以相同 `runId` 生成一张持久的交付或失败结果卡，放在最终 Assistant 总结之后。活动卡和结果卡不同时存在，组件状态也不能复制成两套来源。历史结果卡留在会话中，后续运行使用新的活动槽实例。

### 3. 校验和修复

校验开始时，Agent 可以说明：

> 功能已经生成，我正在检查页面结构、脚本启动和交互行为。

如果校验失败，进度卡切换为修复状态，并在同一位置显示可理解的原因：

> 初次检查发现脚本初始化问题，我正在自动修复，不需要你进行操作。

旧的失败记录保留在详细历史中，但不继续作为当前红色状态展示。重新校验成功后，卡片原位变为通过状态。

### 4. 交付

运行成功后，Agent 输出自然的最终总结，包括完成内容、主要能力、校验结论和必要的使用说明。动态卡变为交付卡，提供：

- 完成摘要
- 校验和构建状态
- 创建或修改文件数量
- `打开应用` 主按钮
- `查看详细过程` 次要入口

访问地址使用新窗口打开，并设置 `target="_blank"` 与 `rel="noopener noreferrer"`。URL 只有在可访问性检查通过后才显示为成功交付入口。

## 自然语言行动说明

### 消息类型

应用生成模式新增明确的用户可见行动说明通道，与技术事件和最终交付分离：

- `opening`：确认目标并概括执行方向；
- `milestone`：说明已完成的重要工作和下一步；
- `validation`：说明开始检查或检查结果；
- `repair`：说明发现的问题和自动修复动作；
- `delivery`：总结结果和使用入口。

这些消息以普通 Assistant Markdown 呈现，支持真实文本增量流式输出。它们不得包含隐藏推理、内部提示词、未经整理的工具参数或安全敏感信息。

### 生成策略

首选由 Agent V2 模型执行过程输出专用 commentary 增量事件，使表达与当前任务上下文自然一致。运行事件仍是状态真相，commentary 只负责解释。

当模型或供应商不支持中途 commentary 时，使用基于真实事件的本地化叙述投影作为降级方案。降级文本必须引用实际阶段、任务类型和结果，不能猜测进度。

### 节流与去重

- 启动说明立即显示。
- 仅在阶段变化、重要成果、校验结论、修复动作或交付时追加持久消息。
- 同一语义阶段的连续事件在短窗口内合并。
- 没有语义变化时只更新进度卡，不新增聊天消息。
- 相同 commentary 的重放按稳定事件 ID 去重。
- 长时间任务可以更新卡片中的当前动作和运行时间，但不发送固定频率的空洞心跳消息。

## 动态进度模型

### 展示状态

原始事件日志和用户展示状态分离。每个运行维护一个派生展示模型：

```ts
type AgentV2RunPresentation = {
	runId: string;
	lifecycle: "running" | "repairing" | "succeeded" | "failed" | "interrupted";
	phase: "intake" | "planning" | "implementation" | "validation" | "repair" | "delivery";
	currentAction: string;
	startedAt: number;
	settledAt?: number;
	tasks: Map<string, TaskPresentation>;
	artifacts: Map<string, ArtifactPresentation>;
	validations: Map<string, ValidationPresentation>;
	diagnostics: DiagnosticPresentation[];
	milestones: MilestonePresentation[];
	delivery?: DeliveryPresentation;
};
```

任务以 `taskId`、产物以 `artifactId`、校验以 `validationId` 原位更新。诊断保留有序历史，但相同诊断重放去重。展示 reducer 必须是纯函数，使实时事件、会话恢复和事件重放得到相同结果。

### 阶段展示

卡片使用有依据的阶段序号，而不是百分比：

1. 理解需求
2. 规划
3. 实现
4. 校验与必要修复
5. 交付

修复是校验阶段中的可重复子流程，不应通过每次重试无限增加总阶段数。当前阶段可以显示活动动画，已完成阶段显示文字和图标，不能只依赖颜色。

### 紧凑状态

运行中的卡片默认显示当前阶段和当前动作，始终保持可读，不要求用户展开。历史成功卡默认收缩为一行摘要；历史失败卡显示一行失败原因和明确的处理入口。

### 详细状态

展开后按以下分组展示：

- 任务：最新任务状态和阶段；
- 文件：创建、修改及最新校验状态；
- 检查：每次校验及修复后的结果；
- Skills：实际应用的 Skill 和按需读取的资源；
- 技术记录：诊断代码、模型、provider 和其他审计信息。

组内相同实体只显示最新状态，并可进一步查看自己的历史变化。默认不平铺全部事件。

## 统一展开协调

### 状态边界

所有展开入口由统一协调器管理，组件不得各自维护无法协调的独立布尔值。协调状态至少包含：

- 当前页面级面板；
- 当前展开的运行详情；
- 当前展开的历史运行；
- 当前运行卡内部详情分组；
- 当前模态弹窗；
- 用户是否手动收起当前自动展开内容。

### 页面级规则

- 文件、应用列表、Skills、诊断和设置等同区域页面级面板一次只展开一个。
- 桌面端侧栏与会话内进度详情没有视觉重叠时可以共存。
- 移动端侧栏变为抽屉后，与会话详情属于同一占用区域；打开其中一个必须关闭另一个。
- 模态弹窗打开时保留底层展开状态但禁止底层交互；关闭后恢复焦点和原状态。

### 会话级规则

- 当前运行卡保持紧凑可见，用户可以展开详细过程。
- 同一时间最多展开一个历史运行详情。
- 用户展开历史运行时不停止当前运行，也不隐藏当前运行的紧凑状态。
- 当前运行详情与历史运行详情在同一区域内互斥。
- 运行结束后不强制打开详情，只将卡片平滑切换为交付或失败摘要。

### 卡片内部规则

- 任务、文件、检查、Skills 和技术记录使用单选手风琴。
- 同一张卡内最多展开一个详情分组。
- 错误首次发生时可以自动显示简短错误摘要，但不自动打开完整技术记录。
- 用户手动收起后，同一错误的重放不得再次强制展开。
- 展开和收起必须使用按钮语义、`aria-expanded` 和明确的视觉指示，不能隐藏原生指示后不提供替代控件。

## 滚动和输入框

- 输入框参与正常布局，消息列表底部预留其真实高度，不允许覆盖最后一条消息或进度卡。
- 只有用户位于底部阈值内时，新增文字和卡片高度变化才自动跟随。
- 用户向上阅读时保持滚动锚点，不因流式文本或详情展开抢回视口。
- 非跟随状态显示 `有新的生成进度` 提示，点击后滚动到最新内容。
- 展开位于当前视口下方的内容时，采用最小必要滚动，不把卡片标题移出视口。
- 会话恢复后不自动展开历史详情，也不自动滚动到旧错误。

## 错误、重试和中断

### 可自动修复

同一进度卡进入 `repairing`，显示首要可理解原因、修复次数和当前动作。历史失败校验进入详细过程，当前顶层状态只表示正在修复。

### 不可自动修复

卡片进入 `failed`，显示：

- 失败阶段；
- 首要原因；
- 已完成工作；
- 是否可安全重试；
- 明确的下一步操作。

完整诊断默认折叠。失败卡不得只显示 `task graph is blocked` 等缺少根因的摘要。

### 中断和连接恢复

- 用户主动停止显示 `已停止`，保留已生成文件和查看详情入口。
- 临时断线显示 `正在恢复连接`，不立即判定任务失败。
- 重连后通过事件序号补齐缺失事件，并从 reducer 重建同一张进度卡。
- 收到终态后停止活动动画和运行时间更新。

## 持久化与兼容

- 原始 Agent V2 事件继续持久化，作为审计和重建来源。
- 新的运行展示消息只保存稳定 `runId` 和必要的展示元数据，不复制完整事件历史。
- 自然语言 commentary 作为普通 Assistant 内容持久化并按增量 ID 去重。
- 重新加载会话时，从原始事件重建每个运行的最终进度卡，不重复追加任务状态。
- 旧版逐事件活动消息继续只读渲染，不能再由新运行产生。
- 历史旧会话无需迁移即可阅读；新的聚合视图只应用于具备 `runId` 和完整事件序列的新运行。

## 视觉与动效

- 延续当前圆角、边框、主题 token 和对话排版，不引入新的视觉体系。
- 自然文字与普通 Assistant 消息一致，保持 Markdown 层级和可复制性。
- 进度卡的紧凑状态应低于正文视觉权重，高于 token/usage 元信息。
- 阶段切换、状态图标和内容高度使用克制的短动效；快速连续事件先合并再呈现，避免卡片闪烁。
- 遵循 `prefers-reduced-motion`，关闭非必要位移动画和循环脉冲。
- 失败使用图标、标题和文字共同表达，不只使用红色。
- 运行计时不进入屏幕阅读器实时播报；当前行动使用节流后的 `aria-live="polite"`。

## 组件边界

### `AgentV2RunPresentationReducer`

消费原始运行事件并产生确定性的展示状态，不依赖 DOM、语言或展开状态。

### `AgentV2NarrationProjector`

合并模型 commentary 与事件驱动降级文本，负责本地化、去重、节流和安全过滤，不修改运行状态。

### `AgentV2ProgressCard`

只负责渲染一个运行的紧凑状态、详细分组和交付/失败动作。它不直接订阅网络事件。

### `AgentV2ActiveRunSlot`

位于消息列表和输入框之间，只承载当前运行的 `AgentV2ProgressCard`。它负责在卡片展开时参与布局测量，并在运行终止后把最终结果交给会话持久层；它不复制运行展示状态。

### `ExpansionCoordinator`

管理页面、会话和卡片内部的区域占用与焦点恢复。组件通过明确动作请求展开，不直接控制其他组件。

### `ConversationFollowController`

维护底部跟随、滚动锚点、新进度提示和输入框高度，不理解 Agent V2 业务事件。

这些组件通过稳定状态和事件接口协作，避免网络处理、业务归并、视觉展开和滚动逻辑重新耦合到单个 bootstrap 文件。

## 测试策略

### 展示 reducer

- 同一任务的 `pending → succeeded` 只产生一个最新任务实体。
- 同一校验失败、修复、重新通过后，顶层状态为通过，历史仍可审计。
- 事件重放和乱序补齐不会重复产物或诊断。
- 实时消费与会话恢复产生相同展示状态。
- 终态停止运行计时和活动状态。

### 自然语言说明

- commentary 增量按 ID 拼接并持久化一次。
- 相同里程碑不会重复生成聊天消息。
- 快速连续事件被合并，长时间无变化不会产生虚假心跳消息。
- provider 不支持 commentary 时使用真实事件驱动的本地化降级文本。
- 输出不会包含隐藏推理、内部提示词或未经整理的工具参数。

### 展开协调

- 桌面端无重叠区域可以共存，同区域面板严格互斥。
- 移动端抽屉、运行详情和历史详情按区域互斥。
- 卡片内部一次只展开一个分组。
- 用户手动收起错误后，相同错误重放不再次强制展开。
- 弹窗关闭后焦点返回触发控件，底层展开状态恢复。

### 滚动和布局

- 输入框不会覆盖最后一条正文、卡片或按钮。
- 用户位于底部时正常跟随流式文字和状态更新。
- 用户向上阅读时视口不被抢占，并出现新进度提示。
- 详情展开保持标题可见并使用最小必要滚动。
- 窄屏、缩放和多行输入框下布局不发生重叠。

### 浏览器验收

1. 生成一个简单静态应用，确认有自然启动说明、阶段性文字和一张动态进度卡。
2. 运行包含多次文件写入的任务，确认不会产生文件或任务卡片墙。
3. 触发一次校验失败和自动修复，确认旧失败不与当前成功状态冲突。
4. 在运行中展开文件详情，再打开诊断或页面级面板，确认互斥规则与焦点正确。
5. 运行中向上滚动，确认新增进度不抢滚动位置。
6. 在移动端视口测试抽屉、详情、输入框和新进度提示无覆盖。
7. 完成后点击 URL，确认新窗口打开应用并保留原会话。
8. 刷新和重连会话，确认自然文字与聚合进度不重复。

## 验收标准

- 应用生成过程包含自然、简短、可流式显示的行动说明，而不是只有状态卡。
- 每个 `runId` 在会话中只有一个动态进度卡。
- 同一任务、产物和校验的状态更新在原位呈现，不产生互相矛盾的顶层卡片。
- Skill、资源、文件和诊断默认聚合在详细过程，不干扰主要对话。
